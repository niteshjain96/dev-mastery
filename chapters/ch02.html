The three-sentence frame for this whole area

Interviewers ask scope, this and prototypes back to back, almost every time. Candidates who sound strongest can separate them in one breath:

Names come from the scope chain, fixed at authoring time. Properties come from the prototype chain, walked at lookup time. this comes from the call.

Learn that sentence now. Every question in this chapter is a detail hanging off one of its three clauses, and saying it early tells the interviewer you have a model rather than a pile of facts.

Session 1 this is decided by the call, not the code ~75 min

1 · How this is determined

Question 1 How is the value of this determined in JavaScript? Near-certain · and the follow-ups run deep
Say this

For a normal function, this is not decided by where the function is written — it is decided by how it is called. MDN calls it runtime binding. There are four call shapes, and they have a precedence order.

One: new Fn() — this is the newly created object. Two: explicit binding — fn.call(obj), fn.apply(obj) or a function produced by fn.bind(obj) — this is that object. Three: a method call, obj.fn() — this is the object left of the dot at the moment of the call. Four: a plain call, fn() — this is undefined in strict mode, and the global object in sloppy mode, where the engine substitutes it.

Arrow functions sit outside all four. They do not have their own this — they take it lexically from the enclosing scope, exactly like any other captured variable, and call, apply and bind cannot change it.

Example — the same function, five call shapes

"use strict";

function whoAmI() { return this; }

const widget = { id: "w1", whoAmI };

whoAmI();                      // undefined        — plain call, strict mode
widget.whoAmI();               // widget           — left of the dot
whoAmI.call({ id: "w2" });     // { id: "w2" }     — explicit
new whoAmI();                  // a fresh object   — new wins over everything

const detached = widget.whoAmI;
detached();                    // undefined        — the dot was not part of the function

That last pair is the entire chapter in four lines. widget.whoAmI does not return "the method of widget" — it returns a plain function value. The binding lived in the call expression, not in the function. Pull the function out of the object and the binding is gone.

2 · call, apply and bind

Question 2 What's the difference between call, apply and bind? Now implement bind. Extremely common · the implementation is a standard machine-coding warm-up
Say this

All three set this explicitly. call and apply invoke immediately and differ only in how arguments are passed — call takes them individually, apply takes an array. bind does not invoke; it returns a new function with this permanently fixed, and it can also pre-fill leading arguments, which makes it partial application.

Three details that separate a good answer from a recited one. The binding from bind is permanent — binding an already-bound function again does nothing, the second thisArg is ignored. A bound function used with new ignores the bound this, because construction creates its own. And a bound function has no prototype property, so it cannot be extended by a class.

Example

function move(dx, dy) { this.x += dx; this.y += dy; return this; }

const widget = { x: 10, y: 20 };

move.call(widget, 5, 5);            // args spread   → { x: 15, y: 25 }
move.apply(widget, [5, 5]);         // args as array → { x: 20, y: 30 }

const moveWidget = move.bind(widget, 100);   // this AND dx pre-filled
moveWidget(0);                      // → { x: 120, y: 30 }

// the three facts people miss
const rebound = moveWidget.bind({ x: 0, y: 0 });
rebound(0);                         // still mutates `widget` — rebinding is ignored

console.log(moveWidget.name);       // "bound move"
console.log(moveWidget.length);     // 1  — original 2 minus 1 pre-filled argument
console.log("prototype" in moveWidget); // false
Invokes now?ArgumentsReturnsTypical use
callYesIndividuallyfn's return valueBorrowing a method once
applyYesAs an arrayfn's return valueSpreading a dynamic argument list
bindNoPre-filled (partial)a new functionPassing a method as a callback
Trap

"apply is for arrays" is a dated answer. With spread syntax, fn.call(obj, ...args) covers almost every case apply used to. Say that — it signals you know the modern idiom rather than reciting an ES5-era table. The one place apply still wins is very old code and Math.max.apply(null, arr) style calls you meet in legacy files.

myCall, myApply and myBind — the new-correct version

// Add all three to Function.prototype. Do not use the built-ins.
//
// myBind must satisfy ALL of these:
//   1. permanent this
//   2. partial application of leading arguments
//   3. when the bound function is used with `new`, the bound this is
//      IGNORED and the instance must still be instanceof the original
//   4. rebinding a bound function does not change this

Function.prototype.myCall = function (thisArg, ...args) { /* you */ };
Function.prototype.myApply = function (thisArg, args) { /* you */ };
Function.prototype.myBind = function (thisArg, ...preset) { /* you */ };

// test 3 is the one that separates answers:
function Widget(id) { this.id = id; }
Widget.prototype.render = function () { return "<" + this.id + ">"; };
const Bound = Widget.myBind({ id: "IGNORED" });
const w = new Bound("w1");
console.log(w.id, w instanceof Widget, w.render());  // "w1" true "<w1>"
Solution — open only after the timer 
Function.prototype.myCall = function (thisArg, ...args) {
  if (typeof this !== "function") throw new TypeError("not callable");
  // a unique key so we never clobber a real property on thisArg
  const key = Symbol("fn");
  const ctx = thisArg ?? globalThis;          // sloppy-mode substitution
  Object.defineProperty(ctx, key, { value: this, enumerable: false, configurable: true });
  try { return ctx[key](...args); }
  finally { delete ctx[key]; }
};

Function.prototype.myApply = function (thisArg, args) {
  return this.myCall(thisArg, ...(args ?? []));
};

Function.prototype.myBind = function (thisArg, ...preset) {
  if (typeof this !== "function") throw new TypeError("not callable");
  const target = this;

  function bound(...later) {
    // new.target is set only when called with `new`.
    // In that case ignore thisArg entirely and use the fresh instance.
    return target.apply(
      new.target ? this : thisArg,
      [...preset, ...later]
    );
  }

  // make `new Bound()` produce something instanceof the ORIGINAL
  if (target.prototype) bound.prototype = Object.create(target.prototype);
  return bound;
};

What is being scored, in the order a reviewer notices:

  • new.target is the clean way to detect construction. The older trick is this instanceof bound, which works but is fragile; saying you know both is the strong answer.
  • Object.create(target.prototype) rather than bound.prototype = target.prototype. Assigning directly means mutating Bound.prototype would corrupt Widget.prototype for every instance.
  • A Symbol key plus finally { delete } in myCall. The common version does thisArg.fn = this, which can overwrite a real property named fn and leaks it if the call throws.
  • Spec fidelity you should mention even if you skip it: the real bind also sets name to "bound " + fn.name and length to max(0, fn.length - preset.length), and a genuine bound function exotic object has no prototype property at all. Our polyfill cannot reproduce that last part in plain JavaScript; saying so out loud is better than pretending.

3 · Arrow vs regular functions

Question 3 What's actually different about an arrow function? Very common · most candidates give one difference and stop
Say this

Arrow functions are not just shorter syntax — they are missing several things a normal function has, deliberately. They have no own this, so this resolves lexically and call, apply and bind cannot change it. They have no arguments object, so you use rest parameters. They cannot be used with new — they are not constructors and have no prototype property. They have no own super or new.target, both of which are also lexical. And they cannot be generators.

The design intent is one sentence: an arrow is meant to be a callback, not a method. Every difference follows from that.

Featurefunction=>Consequence
own thisYes, per callNo — lexicalGreat inside methods, wrong as methods
call/apply/bind can set thisYesNo — silently ignoredarrowFn.call(obj) does nothing
argumentsYesNo — outer oneUse (...args)
newYesNo — TypeErrorNever a constructor
prototype propertyYesNoCannot hold shared methods
super, new.targetOwnLexicalArrows in methods can still call super
Hoisted as a valueYes (declaration)NoTDZ — Chapter 1, row 7
Can be a generatorYesNoNo function* arrow

Example — where each one is correct

class SlideCanvas {
  widgets = [];

  // METHOD → normal function. It needs its own `this` from the call.
  renderAll() {
    // CALLBACK → arrow. It should keep renderAll's `this`.
    this.widgets.forEach((w) => this.drawWidget(w));

    // the pre-arrow workarounds you will still meet in old code:
    this.widgets.forEach(function (w) { this.drawWidget(w); }, this);   // thisArg
    const self = this;                                                   // var self = this
    this.widgets.forEach(function (w) { self.drawWidget(w); });
  }

  // CLASS FIELD ARROW → bound to the instance, one copy per instance.
  // Use when the method will be detached and passed around.
  handlePointerDown = (e) => { this.select(e.target.dataset.id); };
}

4 · Losing this, and the three fixes

Question 4 This handler logs undefined. Why, and give me three different fixes. Very common · often given as live debugging rather than a question 
class WidgetToolbar {
  constructor(widgets) { this.widgets = widgets; }

  handleClick(e) {
    console.log(this.widgets.length);   // TypeError: Cannot read properties of undefined
  }

  mount(el) {
    el.addEventListener("click", this.handleClick);
  }
}
Say this

this.handleClick evaluates to a plain function value — the this binding lives in the call expression, not in the function, so passing it to addEventListener strips it. When the listener fires, the DOM calls it with this set to the element. Class bodies are always strict, and the element has no widgets, so it fails.

Three fixes, and I would pick based on how many instances exist. Bind once in the constructor — this.handleClick = this.handleClick.bind(this) — keeps the method on the prototype and creates one bound copy per instance. A class field arrow — handleClick = (e) => {} — is the cleanest to read, but it is an instance field, so each instance carries its own function and it is no longer on the prototype. Wrap at the call site — el.addEventListener("click", (e) => this.handleClick(e)) — leaves the class untouched but you must keep the wrapper's reference if you ever want to remove the listener.

Trap

Fix three has a cleanup bug that interviewers love: removeEventListener compares by identity. If you pass a fresh arrow to addEventListener and another fresh arrow to removeEventListener, nothing is removed — and you have the exact closure leak from Chapter 1, question 8. Mention it unprompted.

Solution — open only after the timer 
// FIX 1 — bind in the constructor
class ToolbarA {
  constructor(widgets) {
    this.widgets = widgets;
    this.handleClick = this.handleClick.bind(this);  // own prop shadows the prototype method
  }
  handleClick(e) { console.log(this.widgets.length); }
  mount(el)   { el.addEventListener("click", this.handleClick); }
  unmount(el) { el.removeEventListener("click", this.handleClick); }   // same reference ✓
}

// FIX 2 — class field arrow (bound to the instance at construction)
class ToolbarB {
  constructor(widgets) { this.widgets = widgets; }
  handleClick = (e) => { console.log(this.widgets.length); };
  mount(el)   { el.addEventListener("click", this.handleClick); }
  unmount(el) { el.removeEventListener("click", this.handleClick); }   // ✓
}

// FIX 3 — wrap at the call site; you MUST keep the wrapper
class ToolbarC {
  constructor(widgets) { this.widgets = widgets; this._onClick = null; }
  handleClick(e) { console.log(this.widgets.length); }
  mount(el) {
    this._onClick = (e) => this.handleClick(e);    // store it or you can never remove it
    el.addEventListener("click", this._onClick);
  }
  unmount(el) { el.removeEventListener("click", this._onClick); this._onClick = null; }
}

The 500-instance question. Fixes 1 and 2 each allocate one extra function per instance, so 500 instances means 500 functions either way — the difference between them is readability, not memory. Only a plain prototype method is genuinely shared, and a plain prototype method is exactly what cannot be detached. So the honest answer is: the cost is real but tiny, it is identical for both idiomatic fixes, and a few hundred closures is nothing next to the widgets themselves. If you were rendering 50,000 rows it would be worth one delegated listener on the container instead — which is the same conclusion as Chapter 1, question 7.

One more fact worth volunteering: with a class field arrow, handleClick is not on Toolbar.prototype, so a subclass cannot override it with a prototype method and super.handleClick() does not exist. That is the real trade-off, and it is not about memory.

Session 3 The prototype chain ~75 min

5 · The prototype chain

Question 5 What is the prototype chain, and what's the difference between __proto__ and prototype? Near-certain · the __proto__ half is where most answers collapse
Say this

Every object has an internal link to another object called its prototype, and that one has a prototype of its own, until something reaches null. When you read a property, the engine looks on the object itself, then walks that chain until it finds the name or runs out — in which case you get undefined. That walk is the prototype chain, and it is how inheritance works in JavaScript: there are no classes underneath, only objects linked to other objects.

__proto__ and prototype are different things with confusingly similar names. __proto__ — properly Object.getPrototypeOf(obj) — is the link on an object pointing at what it inherits from. prototype is a property on a constructor function holding the object that will become the __proto__ of every instance it creates. So Object.getPrototypeOf(new Widget()) === Widget.prototype. One is the link; the other is the template for the link.

Two consequences worth stating. Writes never walk the chain — assigning to a property always creates an own property that shadows the inherited one. And when an inherited method runs, this is the object you called it on, not the prototype it was found on.

Example — and this one is literally your day job

You already implement a prototype chain by hand. In the .pptx pipeline, a shape's properties resolve through shape → slide → layout → master: if the shape has no explicit fill, you look at the layout; if the layout has none, you fall back to the master. That is exactly the algorithm below, and it is the most convincing way you can explain prototypes in an interview, because it is yours. 

// the real thing, expressed as prototypes
const master = { fill: "#ffffff", fontFamily: "Calibri", fontSize: 18 };
const layout = Object.create(master);          // layout.__proto__ === master
layout.fontSize = 24;                          // layouts override some of the master

const slide = Object.create(layout);
const shape = Object.create(slide);
shape.text = "Q3 revenue";

shape.text;         // "Q3 revenue"  — own property
shape.fontSize;     // 24            — found on layout, two links up
shape.fontFamily;   // "Calibri"     — found on master, three links up
shape.shadow;       // undefined     — walked the whole chain, found nothing

// writes do NOT walk the chain — they shadow
shape.fontSize = 32;
layout.fontSize;    // still 24 — the layout was never touched
delete shape.fontSize;
shape.fontSize;     // 24 again — the inherited value reappears
Seedhi baat

Property dhoondhne ka tareeka bilkul aapke .pptx resolver jaisa hai: pehle shape pe dekho, na mile to slide, phir layout, phir master. Jahan pehli baar mile, wahin ruk jao. Kahin na mile to undefined.

Aur likhte waqt ye chain nahi chalti — likhne par hamesha apni khud ki property banti hai, jo upar wali ko dhak deti hai. Isliye shape.fontSize = 32 layout ko kabhi nahi badalta. Ye ek line bahut se "ye kaise change ho gaya" wale bugs samjha deti hai.

function protoChain(obj) {
  const chain = [];
  let cur = obj;
  while ((cur = Object.getPrototypeOf(cur)) !== null) chain.push(cur);
  chain.push(null);
  return chain;
}

function whoOwns(obj, prop) {
  // Object.hasOwn is the modern, null-prototype-safe check (ES2022).
  // The old form — Object.prototype.hasOwnProperty.call(obj, prop) — also works.
  if (Object.hasOwn(obj, prop)) return "own";
  let cur = obj, depth = 0;
  while ((cur = Object.getPrototypeOf(cur)) !== null) {
    depth++;
    if (Object.hasOwn(cur, prop)) return `prototype chain, ${depth} link(s) up`;
  }
  return "not found";
}

// ["HTMLCanvasElement", "HTMLElement", "Element", "Node", "EventTarget", "Object", undefined]

Second, obj.hasOwnProperty(prop) called directly is a bug waiting to happen: an object created with Object.create(null) does not have it, and any object can shadow it with its own property named hasOwnProperty. Use Object.hasOwn(obj, prop). Knowing why that method was added is a genuinely senior signal.

6 · What new actually does

Question 6 What does the new operator do? Implement it. Very common · the classic polyfill pairing with bind
Say this

new Fn(args) does four things. It creates a new empty object. It sets that object's prototype to Fn.prototype. It calls Fn with this bound to the new object, passing the arguments through. And it returns that object — unless the constructor explicitly returns an object of its own, in which case that one wins. A returned primitive is ignored.

That last clause is the whole interview. Returning an object from a constructor overrides the instance; returning a number, string or undefined does not.

function myNew(Ctor, ...args) {
  if (typeof Ctor !== "function") throw new TypeError(`${Ctor} is not a constructor`);

  // 1 + 2: create the object with the right prototype, in one step.
  // Guard: Ctor.prototype can be null or a primitive if someone reassigned it.
  const proto = (Ctor.prototype !== null && typeof Ctor.prototype === "object")
    ? Ctor.prototype
    : Object.prototype;
  const instance = Object.create(proto);

  // 3: run the constructor with `this` = the new object
  const result = Ctor.apply(instance, args);

  // 4: an OBJECT return wins; anything else is ignored.
  // typeof null === "object", so exclude it explicitly.
  // Functions count as objects here too.
  return (result !== null && (typeof result === "object" || typeof result === "function"))
    ? result
    : instance;
}

Grading notes:

  • Object.create(Ctor.prototype) rather than {} plus setPrototypeOf — one step, and it avoids the de-optimisation MDN warns about.
  • The object-return check must exclude null and must include functions. Missing the null case is the single most common bug in this polyfill.
  • Reading Ctor.prototype once into a local is not just style — it mirrors what the spec does, and it makes the null-prototype guard readable.
  • What this cannot do: it does not set new.target, so a constructor that checks new.target (or an ES2015 class, which throws when called without new) will not work. Say that — myNew(class A {}) throwing is expected behaviour, not a bug in your answer.

The last bullet is the difference between a candidate who memorised four steps and one who understands that new is a syntactic operation the language does not fully expose.

7 · What class desugars to

Question 7 Is class just syntactic sugar over prototypes? Common · "yes" is the wrong answer and they are waiting for it
Say this

Mostly, but not entirely — and the exceptions are the interesting part. The sugar is real: methods go on Class.prototype, extends wires the prototype chains, and instances get their prototype from Class.prototype just as with a constructor function.

What is not sugar: a class body is always strict mode; class declarations are in a temporal dead zone rather than value-hoisted like function declarations; a class constructor cannot be called without new; prototype methods are non-enumerable, so they do not show up in for…in; derived constructors have no this until super() runs; and private # fields are not properties at all — they are a separate mechanism with no prototype involvement and a real brand check.

So the accurate answer is: the inheritance is sugar, the semantics are not.

8 · Inheritance, super and instanceof

Question 8 How does inheritance work, and how would you implement instanceof yourself? Common pairing · the composition follow-up is where seniority shows
Say this

class B extends A wires up two chains, and that is the part people miss. B.prototype's prototype becomes A.prototype, so instances inherit instance methods. And B itself gets A as its prototype, so static methods are inherited too. super() calls the parent constructor; super.method() looks the method up starting one level above the current object's home, not on this.

instanceof is simpler than it looks: it walks the object's prototype chain and asks whether Ctor.prototype appears anywhere in it. It does not compare constructors or names — which is why an object from a different iframe or a different copy of a library fails instanceof even though it looks identical.

Example — both chains, drawn in code

class Widget {
  constructor(id) { this.id = id; }
  render() { return `<widget ${this.id}>`; }
  static from(json) { return new this(json.id); }   // `this` is the subclass when inherited
}

class TextWidget extends Widget {
  constructor(id, text) {
    super(id);                 // must come before any use of `this`
    this.text = text;
  }
  render() {
    return super.render() + `[${this.text}]`;   // explicit parent lookup
  }
}

// chain 1 — instances
Object.getPrototypeOf(TextWidget.prototype) === Widget.prototype;   // true
// chain 2 — the classes themselves (this is the one people forget)
Object.getPrototypeOf(TextWidget) === Widget;                        // true

TextWidget.from({ id: "t1" }) instanceof TextWidget;                 // true — `this` was TextWidget
Trap

super.render() is not this.__proto__.render(). It is resolved from the home object of the method — the object the method was defined on — which is what stops infinite recursion when a three-level hierarchy calls super at each level. If you "desugar" it to this.__proto__, a three-level chain loops forever. That is a favourite whiteboard trap.

function myInstanceof(obj, Ctor) {
  if (typeof Ctor !== "function") throw new TypeError("Right-hand side is not callable");

  // the real operator checks this first — Promise, Array and others use it
  const custom = Ctor[Symbol.hasInstance];
  if (typeof custom === "function") return Boolean(custom.call(Ctor, obj));

  if (obj === null || (typeof obj !== "object" && typeof obj !== "function")) return false;

  const target = Ctor.prototype;
  let cur = Object.getPrototypeOf(obj);
  while (cur !== null) {
    if (cur === target) return true;
    cur = Object.getPrototypeOf(cur);
  }
  return false;
}

const Selectable = (Base) => class extends Base {
  #selected = false;
  select()   { this.#selected = true;  return this; }
  deselect() { this.#selected = false; return this; }
  get isSelected() { return this.#selected; }
};

const Resizable = (Base) => class extends Base {
  resize(w, h) { this.w = w; this.h = h; return this; }
  render() { return super.render() + `[${this.w}x${this.h}]`; }   // super works ✓

Two points to make out loud. First, a mixin that returns a subclass keeps the prototype chain intact, so instanceof and super both still work. The older approach — Object.assign(Widget.prototype, behaviours) — copies methods and gives you neither: no super, no instanceof, and silent collisions when two mixins define the same name.

Second, Symbol.hasInstance is why a hand-rolled instanceof that only walks prototypes is incomplete. It is also the answer to "can instanceof lie?" — yes, any class can define that symbol and decide for itself.

9 · Property descriptors and Object.create

Question 9 How would you make a property read-only, or computed? And what is Object.create for? Moderate · but it is the foundation under freeze, Vue 2 reactivity and immutability talk
Say this

Every property is described by a descriptor, and there are two kinds. A data descriptor has value and writable. An accessor descriptor has get and set instead — that is a computed property. Both also have enumerable, which controls whether it appears in Object.keys, for…in and spread, and configurable, which controls whether the descriptor can be changed or the property deleted.

The default matters: properties created by assignment are writable, enumerable and configurable, but properties created by Object.defineProperty default to false for all three. That asymmetry catches people.

Object.create(proto, descriptors) creates an object with an explicit prototype and optional descriptors in one step. It is how you build a prototype chain without a constructor, and Object.create(null) gives you a genuinely empty dictionary with no inherited keys at all.

Example

const cue = {};

// data descriptor — note every flag defaults to FALSE here
Object.defineProperty(cue, "id", { value: "c1", enumerable: true });
cue.id = "c2";              // silently ignored in sloppy mode, TypeError in strict
Object.keys(cue);           // ["id"]  — because we opted into enumerable

// accessor descriptor — a computed property
Object.defineProperty(cue, "duration", {
  get() { return this.end - this.start; },
  enumerable: false,        // hidden from Object.keys, spread and JSON
  configurable: true,
});

// the same thing in literal syntax
const cue2 = {
  start: 0, end: 4,
  get duration() { return this.end - this.start; },
  set duration(d) { this.end = this.start + d; },
};

// inspect rather than guess
Object.getOwnPropertyDescriptor(cue, "id");
// { value: "c1", writable: false, enumerable: true, configurable: false }
Trap

A non-enumerable property is invisible to Object.keys, the spread operator, Object.assign and JSON.stringify — so a computed duration defined this way disappears when you clone or serialise the object. That is a real bug in editors that round-trip state through JSON.parse(JSON.stringify(x)). Getters are computed at read time; they are not data.

10 · Symbol, Proxy, Reflect and WeakMap

Question 10 What are Symbol, Proxy and WeakMap for? Where would you actually use them? Occasional · strong differentiator when it comes up, because most answers are theoretical
Say this

Symbol is a unique, non-string property key. Two symbols are never equal even with the same description, so they cannot collide — useful for attaching metadata to objects you do not own. Well-known symbols are the language's hook points: Symbol.iterator makes an object work with for…of and spread, Symbol.hasInstance customises instanceof, Symbol.toPrimitive controls coercion.

Proxy wraps an object and intercepts the fundamental operations on it — get, set, has, delete, ownKeys and about a dozen more — via handler traps. Reflect is the matching set of functions that perform those same operations with the default behaviour, so inside a trap you call Reflect.get(...) to do the normal thing after your extra logic.

WeakMap holds keys weakly: if nothing else references a key object, the entry can be collected. That makes it the correct place for metadata keyed by DOM nodes or component instances, because you cannot leak by forgetting to delete. Its keys must be objects, and it is not iterable — deliberately, since enumeration would expose garbage collection timing.

Seedhi baat

Proxy ko aise socho: object aur uske users ke beech mein ek bich ka aadmi khada kar diya. Har get, set, delete pehle us aadmi ke paas jata hai — wo chahe to log kare, validate kare, ya default kaam Reflect se karwa de.

Isi cheez par Vue 3 ki reactivity bani hai: get par "kaun padh raha hai" note karo, set par "jo padh rahe the unhe dobara chalao". Aap already samajhte ho — bas naam nahi pata tha.

Example — three uses you can defend

// 1. Symbol.iterator — make your own type work with for…of and spread
class CaptionTrack {
  constructor(cues) { this.cues = cues; }
  *[Symbol.iterator]() { yield* this.cues; }
}
const track = new CaptionTrack([{ t: 0 }, { t: 5 }]);
[...track];                       // works — because of the symbol, not a method name

// 2. Proxy — validation at the boundary, without touching the object
const validated = new Proxy({ w: 100, h: 100 }, {
  set(target, prop, value, receiver) {
    if ((prop === "w" || prop === "h") && (typeof value !== "number" || value <= 0))
      throw new RangeError(`${prop} must be a positive number, got ${value}`);
    return Reflect.set(target, prop, value, receiver);   // then do the normal thing
  },
});
validated.w = 0;                  // RangeError

// 3. WeakMap — per-node metadata that cannot leak
const hitAreas = new WeakMap();
function cacheHitArea(node, rect) { hitAreas.set(node, rect); }
// when the node is removed from the DOM and dropped, the entry goes with it.
// A plain Map here would retain every node you ever measured.

// 1 — negative indices
function negativeIndex(arr) {
  return new Proxy(arr, {
    get(target, prop, receiver) {
      if (typeof prop === "string" && /^-\d+$/.test(prop)) {
        const i = target.length + Number(prop);
        return i >= 0 ? target[i] : undefined;
      }
      return Reflect.get(target, prop, receiver);
    },
  });
}
const a = negativeIndex([10, 20, 30]);
a[-1];        // 30
a.length;     // 3   — untouched
[...a];       // [10,20,30]

// 2 — defaults on read only
function withDefaults(obj, fallback) {
  return new Proxy(obj, {
    get(target, prop, receiver) {
      return Reflect.has(target, prop) ? Reflect.get(target, prop, receiver) : fallback;
    },
    // deliberately NO `has` or `ownKeys` trap, so `in` and Object.keys stay honest
  });
}

// 3 — WeakMap privacy (the pre-#private idiom, still useful)
const secrets = new WeakMap();          // module scope — not exported

export class Session {
  constructor(token) { secrets.set(this, { token }); }
  isValid() { return secrets.get(this).token.length > 10; }
}

The comparison. #private is simpler, is enforced by the language, gives a real brand check with #x in obj, and shows clear intent. The WeakMap version can be shared between a class and module-level helper functions that are not part of the class, works on objects you did not construct, and can attach state to instances of a class you do not own — which #private can never do. Default to #; reach for the WeakMap when the state has to be reachable from outside the class body but still invisible to callers.

Two Proxy details worth saying: always finish a trap with the matching Reflect call rather than touching target directly, because Reflect forwards the receiver and so keeps getters and inheritance correct. And Proxy has a genuine cost — every operation goes through a trap, so it is right for a validation boundary or a devtools-only wrapper, and wrong inside a canvas render loop.

Cross-questions

Map versus WeakMap — when do you choose which?

Testing: do you know the trade-off is memory, not features?

"WeakMap when the key is an object whose lifetime I do not control — DOM nodes, component instances, third-party objects — because entries disappear with the key and I cannot leak by forgetting to clean up. Map when I need iteration, size, primitive keys, or when I genuinely want the entries to outlive their keys, like a cache. The cost of WeakMap is that you can never enumerate it, and that is deliberate: enumeration would let you observe when GC ran."

Where have you seen Proxy in real libraries?

Testing: is this theoretical for you?

"Vue 3's reactivity is built on it — the get trap tracks which effect is reading a property and the set trap re-runs those effects; that is why Vue 3 handles added properties and arrays correctly where Vue 2's defineProperty approach could not. Immer uses proxies to record mutations on a draft and produce an immutable next state. MobX uses them for observables. Knowing why Vue 3 switched is the version of this answer that lands."

What is Symbol.for and how is it different from Symbol()?

Testing: depth on a small API.

"Symbol() always creates a brand-new unique symbol, even with the same description. Symbol.for('key') looks up a global registry shared across the whole realm and returns the same symbol every time — so two independent scripts can agree on a key. Use Symbol() for privacy-ish local metadata and Symbol.for for cross-library protocols."

Are symbol-keyed properties private?

Testing: precision about what "hidden" means.

"Hidden, not private. They are skipped by Object.keys, for…in and JSON.stringify, but Object.getOwnPropertySymbols and Reflect.ownKeys expose them, so anyone determined can read them. For real privacy the tools are # fields or a closure or a WeakMap. Symbols solve collision, not access control."

What is WeakRef, and would you use it?

Testing: honesty about advanced features.

"A WeakRef holds a single object weakly and you call .deref() to try to get it back, which may return undefined if it has been collected. FinalizationRegistry lets you register a cleanup callback. Both come with an explicit warning in the spec against relying on them, because GC timing is not observable behaviour you should build on. I have not needed either in product code — the honest use cases are caches of expensive objects that can be rebuilt. I would not introduce one in an interview answer unless asked."

Chapter 2 — this, prototypes, classes26 questions
What decides the value of this?

How the function is called, not where it is written. Four rules in order: new, explicit binding, method call, plain call.

What is this in a plain call?

undefined in strict mode; globalThis in sloppy mode via this-substitution.

What is this at the top of an ES module?

undefined. In a classic script it is globalThis; in CommonJS it is module.exports.

Why does const f = obj.method; f() break?

The binding lives in the call expression, not the function. You took the function and left the dot behind.

Can call change an arrow function's this?

No. The thisArg is silently ignored — an arrow has no own this to set.

Arrow inside an object literal — what is this?

Whatever it was outside the literal. Object literals do not create a this scope, so it is not the object.

Five things arrows lack.

Own this, arguments, new/constructability, a prototype property, own super and new.target. Also cannot be generators.

call vs apply?

Identical except argument form — individually vs an array. Spread has largely retired apply.

Can you rebind a bound function?

No. The second thisArg is ignored because the target is already bound.

new on a bound function?

The bound this is ignored; construction makes its own. Pre-filled arguments still apply.

What is new.target?

undefined on a normal call, the constructor on a new call. How you detect construction.

bound.name and bound.length?

"bound " + name, and the original length minus the number of pre-filled arguments, floored at 0.

__proto__ vs prototype?

__proto__ is the link on an object; prototype is the property on a constructor holding the object instances will link to.

Do writes walk the prototype chain?

No — a plain assignment creates an own property that shadows. The exception is a setter or a non-writable property found on the chain.

What is this inside an inherited method?

The object you called it on, not the prototype it was found on.

Why avoid Object.setPrototypeOf?

It invalidates engine optimisations built on the object's shape and chain. Set the prototype at creation instead.

The four steps of new.

Create an object; set its prototype to Fn.prototype; call Fn with this as that object; return it unless the constructor returned an object.

What if a constructor returns a primitive?

Ignored — the instance is returned. Only an object (or function) return overrides it.

Is class pure sugar?

No. Always strict, TDZ rather than value hoisting, cannot be called without new, methods non-enumerable, no this before super(), and # fields are a separate mechanism.

Where do class methods live? And instance fields?

Methods on Class.prototype, shared. Fields on each instance, initialised before the constructor body (or right after super()).

Why can't you use this before super()?

A derived constructor has no this of its own — super() is what creates it. Touching it first is a ReferenceError.

How do you brand-check a private field?

#x in obj inside the class body — returns a boolean instead of throwing. Reading obj.#x on a foreign object is a TypeError.

What does extends actually link?

Two chains: B.prototype → A.prototype for instance methods, and B → A for statics.

What does super.m() resolve against?

The method's home object's prototype — not this. Otherwise three-level hierarchies would recurse forever.

When does instanceof lie?

Across realms (iframes, workers), with two copies of a library, and whenever a class defines Symbol.hasInstance.

Spread — what exactly does it copy?

Enumerable own properties by value, invoking getters, dropping the prototype. Use getOwnPropertyDescriptors for a faithful copy.
