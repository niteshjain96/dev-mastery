Async JavaScript: Event Loop, Promises, Generators

This chapter contains the single most reliable whiteboard question in frontend interviewing: a twenty-line snippet with setTimeout, a promise chain and an async function, and the instruction “tell me the order of the output.” Getting it right is not memory. It is one rule applied five times.

5 sessions ~6.25 hours 10 Q-blocks 10 timed drills Prerequisites: Chapters 1–2
The one rule this whole chapter hangs on

Run all the synchronous code. Then drain the entire microtask queue. Then let the browser render. Then take exactly one task. Repeat.

Every ordering puzzle you will ever be given is that sentence applied carefully. Promises and await produce microtasks; setTimeout and events produce tasks. If you can say which of the two a line produces, you can predict the output without running it.

Session 1 The event loop, tasks and microtasks ~75 min

1 · The event loop

Question 1 Explain the event loop. Near-certain · and usually the setup for a puzzle two questions later
Say this

JavaScript runs on a single thread with one call stack, and it is run-to-completion: once a piece of code starts, it finishes before anything else runs. Nothing can preempt it. That is why you never get torn state or data races the way you would in a multithreaded language.

Anything asynchronous — a timer, a network response, a click, a resolved promise — does not interrupt. It queues a job. The event loop is the thing that pulls those jobs out and runs them, one at a time, only ever when the stack is empty.

There are two queues, not one, and the priority between them is the whole game. Microtasks — promise callbacks, await resumptions, queueMicrotask, MutationObserver — are drained completely after the current job, before anything else. Tasks — setTimeout, DOM events, I/O callbacks — are taken one at a time. And the browser only gets a chance to render between tasks, after the microtask queue is empty.

Seedhi baat

Ek line mein: microtask queue puri khali hoti hai, task queue se sirf ek aata hai.

Isliye Promise.then hamesha setTimeout(fn, 0) se pehle chalta hai — chahe timer pehle likha ho. Timer task hai, promise microtask hai, aur microtask ki line pehle khatam hoti hai.

Aur dhyan do: microtask ke andar naya microtask banega to wo bhi isi round mein chalega. Agar loop bana diya, to browser kabhi render hi nahi karega — tab hang ho jayega. Task ke saath ye problem nahi hoti.

H lands between the microtasks and the timers, because requestAnimationFrame callbacks run in the render step.

The variation worth doing properly: move Promise.resolve().then() inside the setTimeout callback and the promise now runs after that timer, because the microtask queue is drained after every task, not once per program.

Cross-questions

Is the event loop part of JavaScript or part of the browser?

Testing: do you know where the boundary is?

"It's part of JavaScript."

"The language spec defines jobs and a job queue, and guarantees run-to-completion. The two-queue model with tasks, microtasks and a render step is defined by the HTML spec — it is the host environment. That is why Node has the same microtask semantics but a different task model, with phases and setImmediate and process.nextTick sitting ahead of promises."

Does setTimeout(fn, 0) run after 0 milliseconds?

Testing: do you know it is a minimum, not a promise?

"No — it schedules a task to run no sooner than 0ms, once the stack is empty and the microtask queue has drained. Browsers also clamp nested timers to about 4ms after five levels of nesting, and background tabs throttle much harder. So it means 'soon, after the current work', not 'immediately'."

If JavaScript is single-threaded, how does it do anything concurrently?

Testing: the host-versus-language distinction again, in practical terms.

"The JavaScript is single-threaded; the host is not. Timers, network requests, file I/O and rendering are handled by the browser or by libuv in Node on other threads, and they hand results back by queueing a job. So the concurrency is real, it just never runs two pieces of your JavaScript at once. For actual parallel JavaScript you need Web Workers, which are separate agents with their own stack, heap and queue — which is why you can only pass messages, not share objects."

Where does requestAnimationFrame fit?

Testing: rendering awareness — relevant to your canvas work.

"It is not a task or a microtask — its callbacks run in the render step, after microtasks drain and immediately before style, layout and paint. That is exactly why it is the right place for canvas drawing: you run once per frame, right before the browser paints, rather than fighting a timer. It also does not run at all in a background tab, which a setInterval redraw would."

2 · Tasks vs microtasks in practice

Question 2 What's the difference between a task and a microtask, and when does it actually matter? Common · the "when does it matter" half is the differentiator
Say this

Mechanically: after each task the engine drains the entire microtask queue, including microtasks queued while draining. Tasks are taken one per loop turn, with a rendering opportunity in between.

It matters in three concrete places. Ordering — a promise callback always beats a setTimeout(fn, 0) written above it. Starvation — a microtask that keeps queueing microtasks will freeze the page completely, because the browser never reaches the render step; the same loop written with setTimeout stays responsive. Batching — if you want several state changes to be seen as one, you coalesce them in a microtask; if you want the browser to paint in between, you need a task or a frame.

Solution — open only after the timer 
function processInChunks(items, workFn, { chunkMs = 8, signal } = {}) {
  return new Promise((resolve, reject) => {
    let i = 0;

    function runChunk() {
      if (signal?.aborted) return reject(signal.reason);

      const deadline = performance.now() + chunkMs;
      // burst synchronously until the time budget is spent
      while (i < items.length && performance.now() < deadline) {
        workFn(items[i], i);
        i++;
      }

      if (i >= items.length) return resolve();

      // yield as a TASK, not a microtask — a microtask would never
      // let the browser paint, which is the whole point
      setTimeout(runChunk, 0);
    }

    runChunk();
  });
}

Three things worth saying out loud when you present this. The budget is time, not count. "Do 50 items then yield" is wrong, because item cost varies; 8ms of a 16.7ms frame leaves room to paint. The yield must be a task. Swap in queueMicrotask and the function still completes, but the page is frozen throughout — the microtask queue never empties, so the render step is never reached. Cancellation is part of the job, because the user can navigate away mid-parse.

The production-grade version uses scheduler.postTask() where available with a priority, or requestIdleCallback for genuinely background work, or a Web Worker if the parse is heavy enough to deserve a real thread. Naming that progression — chunking, then idle callbacks, then a worker — is a strong answer to "how would you parse a large file without freezing the UI", which is exactly what your .pptx importer does.

Why would you ever use queueMicrotask over Promise.resolve().then?

Testing: have you read the guidance, or is it cargo cult?

"Same queue, but queueMicrotask states the intent and avoids the promise quirks — MDN points out that an exception thrown in a promise-created microtask surfaces as an unhandled rejection rather than a normal error. Testing: applied judgement rather than definitions.

"None of them per update — batch. "Microtasks behave the same, but the task side is different: Node's loop has phases — timers, pending callbacks, poll, check, close — and setImmediate fires in the check phase, so setTimeout(fn,0) versus setImmediate ordering at the top level is genuinely non-deterministic. Session 2 Promises, properly ~75 min

3 · What a promise actually is

Question 3 What is a Promise? Walk me through the states. Very common · the resolved-vs-fulfilled distinction is the senior marker
Say this

A promise is an object representing the eventual result of an asynchronous operation. It has three states: pending, fulfilled with a value, or rejected with a reason. Once it leaves pending it is settled, and settling is permanent — a promise cannot change state twice, and later calls to resolve or reject are ignored.

The distinction worth knowing is resolved versus fulfilled. Fulfilled means it succeeded with a value. Resolved means it has been locked in to follow something else — and if you resolve a promise with another promise, it is resolved but still pending until that inner one settles. So "resolved" does not mean "done".

Two guarantees make promises composable. Callbacks always run asynchronously, as microtasks, even if the promise is already settled when you attach them — so a function is never sometimes-sync and sometimes-async. And then always returns a new promise, which is what makes chaining work: returning a value fulfills the next one, throwing rejects it, and returning a thenable makes it adopt that thenable's state.

Example

// settling is permanent
const p = new Promise((resolve, reject) => {
  resolve("first");
  resolve("second");      // ignored
  reject(new Error("no")); // ignored
});

// resolved but NOT fulfilled — still pending for one second
const slow = new Promise((resolveOuter) => {
  resolveOuter(new Promise((resolveInner) => setTimeout(resolveInner, 1000)));
});

// callbacks are ALWAYS async, even on an already-settled promise
const done = Promise.resolve(777);
done.then((v) => console.log("2nd:", v));
console.log("1st: sync");        // this logs first, always

// chaining: each link returns a NEW promise
fetchSlide(id)
  .then((raw) => parseSlide(raw))        // value → next promise fulfills
  .then((slide) => { throw new Error("bad layout"); })  // throw → next rejects
  .then((x) => console.log("skipped"))   // no onRejected → passes the rejection through
  .catch((e) => console.warn(e.message)) // handled here
  .finally(() => hideSpinner());         // runs either way, passes state through
Trap

.finally() does not receive the value or the reason, and it passes the original settled state through — unless it throws or returns a rejected promise, in which case it overrides. People expect it to behave like a then with one argument; it does not.

//   new MyPromise((resolve, reject) => ...)

class MyPromise {

Do not attempt thenable adoption at level 2. Get the state machine right first — that is what is actually being tested.

Solution — open only after the timer 
class MyPromise {
  #state = "pending";
  #value = undefined;
  #callbacks = [];          // queued while pending

  constructor(executor) {
    const resolve = (value) => this.#settle("fulfilled", value);
    const reject  = (reason) => this.#settle("rejected", reason);
    try { executor(resolve, reject); }          // executor is SYNCHRONOUS
    catch (err) { reject(err); }                // a throw in the executor rejects
  }

  #settle(state, value) {
    if (this.#state !== "pending") return;      // one-way, permanent
    this.#state = state;
    this.#value = value;
    this.#callbacks.forEach((cb) => queueMicrotask(cb));
    this.#callbacks = [];
  }

  then(onFulfilled, onRejected) {
    return new MyPromise((resolve, reject) => {
      const handle = () => {
        const handler = this.#state === "fulfilled" ? onFulfilled : onRejected;

        // no handler → pass the state straight through (this is what
        // makes .catch at the end of a chain work)
        if (typeof handler !== "function") {
          this.#state === "fulfilled" ? resolve(this.#value) : reject(this.#value);
          return;
        }

        try {
          const result = handler(this.#value);
          // LEVEL 3 of fidelity: adopt a returned thenable
          if (result && typeof result.then === "function") result.then(resolve, reject);
          else resolve(result);
        } catch (err) {
          reject(err);                          // a throw in a handler rejects the NEXT promise
        }
      };

      // already settled → still async. pending → queue it.
      if (this.#state === "pending") this.#callbacks.push(handle);
      else queueMicrotask(handle);
    });
  }

  catch(onRejected) { return this.then(undefined, onRejected); }

  finally(onFinally) {
    return this.then(
      (v) => { onFinally(); return v; },           // pass the value through
      (e) => { onFinally(); throw e; }             // pass the rejection through
    );
  }

  static resolve(v) { return v instanceof MyPromise ? v : new MyPromise((res) => res(v)); }
  static reject(e)  { return new MyPromise((_, rej) => rej(e)); }
}

The five things being graded, in the order a reviewer checks them:

  • The executor runs synchronously, and a throw inside it rejects. Most first attempts wrap it in a timeout.
  • #settle guards on state — the one-way transition. Without the guard, resolve(); reject(); flips it.
  • Callbacks attached before settling are queued and flushed on settle. This is the part people forget, and it is why the array exists.
  • queueMicrotask even when already settled — the never-sometimes-sync guarantee. Calling the handler directly is the classic bug.
  • Pass-through when a handler is missing — this single branch is why a .catch() five links down still receives an error thrown at the top.

What this deliberately does not do: the real resolution procedure handles a thenable passed to resolve() itself (not just returned from a handler), guards against a promise resolving with itself, and only calls a thenable's then once. Saying "this is not Promises/A+ compliant, here are the three places it diverges" is a much stronger finish than pretending it is.

Cross-questions

Why must callbacks be asynchronous even for an already-settled promise?

Testing: do you know the reason, or just the rule?

"To remove a whole class of bug where a function is sometimes synchronous and sometimes not — 'releasing Zalgo'. If .then ran immediately on a settled promise, then whether your code ran before or after the next line would depend on cache state or network timing. Guaranteeing a microtask makes the ordering deterministic regardless."

What is the difference between returning a value and returning a promise from .then?

Testing: chaining semantics, and it sets up the flattening question.

"A plain value fulfills the next promise immediately. A thenable makes the next promise adopt it — it stays pending until the inner one settles, and then takes its state. That is what lets you flatten async steps into a linear chain instead of nesting. It also costs extra microtask ticks, which is why promise-returning handlers show up later in ordering puzzles than you would guess."

Can a promise be cancelled?

Testing: a favourite. The right answer has two halves.

"Yes, with Promise.cancel."

"No — a promise represents a result, not the operation, and there is no cancel in the API. What you cancel is the underlying work: AbortController with fetch, or a flag that makes the handler ignore a late result. The promise still settles; you just stop caring. That is question 9 in this chapter, and it is the one that actually matters in React cleanup."

What happens to a rejection nobody handles?

Testing: operational awareness.

"It becomes an unhandled rejection: the browser fires an unhandledrejection event on window and logs it; Node terminates the process by default in modern versions. Attaching a handler later, in a different task, is too late — it has already been reported. In production I listen for unhandledrejection and forward it to error monitoring, because otherwise those failures are invisible."

4 · The ordering puzzle

Question 4 What's the output order? The single most common whiteboard exercise in JavaScript rounds
Say this — the method, not an answer

Do not try to read it holistically. Work it mechanically in three passes. Pass one: read top to bottom and write down only the synchronous logs, in order — remembering that an async function body runs synchronously until its first await. Pass two: list the microtasks in the order they were queued, then play them out, appending any new microtasks to the end of the list. Pass three: the tasks, in timer order.

Narrate the passes out loud while you write. Interviewers score the method as much as the answer, and if you make an arithmetic slip while visibly applying the right algorithm, that reads far better than a confident wrong list.

Example — the canonical version, worked

console.log("1");

setTimeout(() => console.log("2"), 0);

async function foo() {
  console.log("3");
  await bar();                 // bar() runs NOW; the await suspends after it
  console.log("4");
}

async function bar() { console.log("5"); }

new Promise((resolve) => {
  console.log("6");            // executor is SYNCHRONOUS
  resolve();
}).then(() => console.log("7"));

foo();

console.log("8");
Work it before reading — three passes, on paper

Pass 1 (sync): 1, then the timer is scheduled, then the promise executor runs → 6, and .then is queued. Then foo() is called: 3, then bar() is called and runs to completion → 5, and the await suspends foo and queues its continuation. Then 8. So: 1, 6, 3, 5, 8.

Pass 2 (microtasks, in queue order): the .then was queued before foo's continuation, so 7, then 4.

Pass 3 (tasks): 2.

Final: 1, 6, 3, 5, 8, 7, 4, 2.

Solution — open only after the timer

A: a1, sync, a2, p. The body runs synchronously to the await. await 1 wraps a non-promise in an already-fulfilled promise and still suspends for one tick — queued before the .then, because a() was called first. MDN is explicit: even an already-fulfilled promise pauses until the next tick.

B: B1, B3, B2. The inner promise is created during the first microtask, so its callback goes to the back of the queue — behind B3, which was already registered on the chain. This is the puzzle that catches the most people. An inner .then is not "nested", it is just later.

C: C1, C3, C4, C5, C2 x. Returning a promise from a handler costs two extra ticks — one to adopt the thenable, one to unwrap it — so C2 falls behind a three-link plain chain. If the handler had returned "x" directly, C2 would have printed second. This is the single best question for separating people who memorised "promises are microtasks" from people who understand adoption.

D: D1, D2, D3, D4. The microtask queue is drained after every task, not once per program. So the first timer's promise runs before the second timer starts. If you predicted D1, D3, D2, D4, that is the one-drain-per-program misconception, and it is worth fixing now.

5 · What async/await really is

Question 5 What does async/await actually do under the hood? Very common · "it's just syntactic sugar" is only half the answer
Say this

async does two things: it makes the function always return a promise, and it permits await inside. If the body returns a value, the promise fulfills with it; if it throws, the promise rejects.

await splits the function in half. Everything up to the first await runs synchronously. At the await, the expression is evaluated, control returns to the caller, and the rest of the function is registered as a continuation to run in a microtask once the awaited value settles. The function's local state — variables, the position in the loop — is preserved across that suspension.

Mechanically it is the same machinery as a generator: a function that can pause and resume, driven by a runner that feeds it promise results. That is exactly how Babel transpiles it, and it is why async/await could be specified on top of things the language already had.

Example — the same function, three ways

// 1. promise chain
function loadSlide(id) {
  return fetchSlide(id)
    .then((raw) => parseSlide(raw))
    .then((slide) => renderThumb(slide))
    .catch((e) => { log(e); return null; });
}

// 2. async/await — identical semantics, linear shape
async function loadSlide(id) {
  try {
    const raw = await fetchSlide(id);
    const slide = await parseSlide(raw);
    return await renderThumb(slide);
  } catch (e) { log(e); return null; }
}

// 3. what it desugars to — a generator plus a driver
function loadSlide(id) {
  return run(function* () {
    const raw = yield fetchSlide(id);      // yield == await
    const slide = yield parseSlide(raw);
    return yield renderThumb(slide);
  });
}

await ko "rukna" mat samjho — function do tukdon mein kat jata hai. Pehla tukda abhi chalta hai, doosra tukda baad mein microtask banke chalta hai. Thread kahin nahi rukta; sirf ye function apni jagah pe pause hota hai aur baaki page chalta rehta hai.

Isliye async function call karne se turant kaam hota hai — pehle await tak. Ye baat interview mein bahut poochi jaati hai.

}).then((v) => console.log("result", v));   // caught inside: boom / result 3
Solution — open only after the timer 
function run(genFn) {
  const gen = genFn();

  return new Promise((resolve, reject) => {
    function step(method, arg) {
      let result;
      try {
        result = gen[method](arg);          // "next" or "throw"
      } catch (err) {
        return reject(err);                 // generator threw and did not catch it
      }

      if (result.done) return resolve(result.value);

      // normalise: a yielded non-promise still goes through a tick,
      // exactly like `await 2`
      Promise.resolve(result.value).then(
        (value) => step("next", value),     // resume with the value
        (error) => step("throw", error)     // throw AT the yield point
      );
    }

    step("next", undefined);                // start it
  });
}

The line that matters is step("throw", error). That is what makes try/catch work inside an async function: the rejection is not passed as a value, it is thrown at the suspension point, so ordinary synchronous error handling applies. Being able to say that sentence is the whole point of the exercise.

Note also Promise.resolve(result.value): it normalises non-promises so yield 2 behaves like await 2 — one tick, not zero. And the outer try/catch around gen[method]() handles a generator that throws synchronously between yields.

Say this

Two different bugs. The first is accidental sequencing: awaiting inside the loop means each request waits for the previous one to finish. Thirty slides at 200ms each is six seconds instead of 200 milliseconds. The fix is to start all the promises first and await them together with Promise.all.

7 · all, allSettled, race and any

Question 7 Difference between Promise.all, allSettled, race and any? Very common · the empty-array cases are the follow-up nobody expects
Say this

all — fulfills with an array of all values when every input fulfills; rejects immediately with the first rejection reason. Fail-fast, all-or-nothing. allSettled — never rejects; waits for everything and gives you an array of { status, value } or { status, reason } objects. race — settles with whichever input settles first, fulfilled or rejected. A fast rejection wins. any — fulfills with the first fulfillment, ignoring rejections; only rejects if they all reject, and then with an AggregateError whose .errors array holds every reason.

The empty-array behaviour is the detail they probe: all and allSettled fulfill immediately with []; race stays pending forever; any rejects immediately with an AggregateError.

The ordering requirement is the whole exercise. If you push results as they arrive, you have written a bug that passes a naive test and fails a real one.

Solution — open only after the timer 
function myAll(iterable) {
  return new Promise((resolve, reject) => {
    const items = [...iterable];               // accept any iterable
    const results = new Array(items.length);   // index-addressed, not pushed
    let remaining = items.length;

    if (remaining === 0) return resolve([]);   // empty → fulfils immediately

    items.forEach((item, i) => {
      Promise.resolve(item).then(
        (value) => {
          results[i] = value;                  // INPUT order preserved
          if (--remaining === 0) resolve(results);
        },
        reject                                 // first rejection wins; later ones are ignored
      );
    });
  });
}

function myAllSettled(iterable) {
  return new Promise((resolve) => {
    const items = [...iterable];
    const results = new Array(items.length);
    let remaining = items.length;
    if (remaining === 0) return resolve([]);

    items.forEach((item, i) => {
      Promise.resolve(item).then(
        (value)  => { results[i] = { status: "fulfilled", value }; },
        (reason) => { results[i] = { status: "rejected", reason }; }
      ).finally(() => { if (--remaining === 0) resolve(results); });
    });
  });
}

function myRace(iterable) {
  return new Promise((resolve, reject) => {
    // no empty check needed: with no inputs nothing ever settles it,
    // which IS the specified behaviour — pending forever
    for (const item of iterable) Promise.resolve(item).then(resolve, reject);
  });
}

function myAny(iterable) {
  return new Promise((resolve, reject) => {
    const items = [...iterable];
    const errors = new Array(items.length);
    let remaining = items.length;

    if (remaining === 0)
      return reject(new AggregateError([], "All promises were rejected"));

    items.forEach((item, i) => {
      Promise.resolve(item).then(
        resolve,                               // first fulfilment wins
        (err) => {
          errors[i] = err;
          if (--remaining === 0)
            reject(new AggregateError(errors, "All promises were rejected"));
        }
      );
    });
  });
}

Five things being graded:

  • Index assignment, not push. Results must be in input order regardless of completion order.
  • A counter, not results.length. Checking length fails on sparse assignment and on inputs containing undefined.
  • Promise.resolve(item) so plain values and thenables both work.
  • The four different empty-input behaviours — and noticing that race needs no special case at all, because doing nothing is the correct behaviour. That observation reads well.
  • Resolving the outer promise more than once is harmless — the state machine ignores later calls — which is why passing reject directly as the rejection handler in myAll is correct and not sloppy.

8 · Errors in async code

Question 8 How do you handle errors in asynchronous code? Common · and a live-debugging favourite
Say this

With async/await, a rejection is thrown at the await, so ordinary try/catch works — that is the main reason to prefer it over chains. In a chain, errors propagate down to the nearest .catch, and a .then without an onRejected handler passes the rejection through untouched.

Four things go wrong in practice. A try/catch around a call you did not await catches nothing — the function has already returned by the time the promise rejects. A .catch placed before the failing step in a chain does not see it; position matters. Errors thrown inside a setTimeout callback or an event handler are in a different task entirely and cannot be caught by the surrounding code at all. An async callback passed to something not async-aware — forEach, an event listener — produces an unhandled rejection.

As a safety net I always register a global unhandledrejection listener that reports to monitoring, because those failures are otherwise invisible.

Example — four ways the catch does not fire

// 1 — missing await: the function returns before the rejection happens
async function save() {
  try {
    persist();                // ✗ no await → catch can never run
  } catch (e) { report(e); }
}

// 2 — return without await inside try (the subtle one)

9 · Cancellation and race conditions

Question 9 A user types fast in a search box. Responses come back out of order. How do you fix it? Common · and it is the exact bug in half of all typeahead implementations
Say this

This is the stale-response race. Request for "ca" is slow, request for "cat" is fast, "cat" renders, then "ca" arrives and overwrites it — so the user sees results for what they typed two keystrokes ago. Debouncing reduces how often it happens; it does not fix it, because two requests can always be in flight.

There are three real fixes and they compose. Abort the previous request with an AbortController, so the stale one is cancelled at the network level rather than merely ignored. Guard the write — keep a request id or a captured query string and discard any response that is not the latest. And in React, the effect cleanup sets an ignore flag, which also covers unmount.

Promises themselves cannot be cancelled — a promise is a result, not an operation. What you cancel is the underlying work, and what you guard is the write.

Example — all three layers

function createSearch(onResults) {
  let controller = null;
  let latest = 0;

  return async function search(query) {
    controller?.abort();                    // 1. cancel the previous request
    controller = new AbortController();
    const id = ++latest;                    // 2. capture a sequence number

    try {
      const res = await fetch(`/api/search?q=${encodeURIComponent(query)}`,
        { signal: controller.signal });
      const data = await res.json();

      if (id !== latest) return;            // 3. a newer request started — drop this
      onResults(data);
    } catch (err) {
      if (err.name === "AbortError") return; // expected, not a failure
      throw err;
    }
  };
}
// the React shape of the same idea — Chapter 14 goes deeper
useEffect(() => {
  let ignore = false;
  const controller = new AbortController();

  (async () => {
    try {
      const data = await fetchSlides(query, { signal: controller.signal });
      if (!ignore) setSlides(data);         // guard the write
    } catch (e) {
      if (e.name !== "AbortError" && !ignore) setError(e);
    }
  })();

  return () => { ignore = true; controller.abort(); };   // cleanup does both
}, [query]);

      );

How does React Query handle this?

It also passes an AbortSignal into the query function so you can cancel properly, and it dedupes identical in-flight requests. That is a large part of why I would not hand-roll this in a product codebase."

10 · Generators, iterators and async iteration

Question 10 What are generators and iterators for? Have you used them? Occasional · strong differentiator, because most answers are "I know the syntax"
Say this

The iterator protocol is an object with a next() method returning { value, done }. The iterable protocol is an object with a [Symbol.iterator]() method returning one of those. Anything that implements it works with for…of, spread, destructuring and Array.from — which is how arrays, strings, Map, Set and NodeList all share the same syntax.

A generator is the easy way to produce one. function* plus yield gives you a function that pauses and resumes, keeping its local state, and the object it returns is both an iterator and an iterable.

Three genuine uses. Lazy or infinite sequences — values are computed on demand, so you can model an unbounded stream without materialising it. Custom iteration over your own data structures, so consumers use plain for…of instead of learning your API. And async iteration — async function* with for await…of is the natural shape for paginated APIs and streams.

Example — three uses from your own domain

// 1. lazy — walk a widget tree without building an array of 10,000 nodes
function* walk(node) {
  yield node;
  for (const child of node.children ?? []) yield* walk(child);   // yield* delegates
}

for (const w of walk(slideRoot)) {
  if (w.type === "image") preload(w.src);
}

// 2. your own type becomes iterable
class CaptionTrack {
  #cues = [];
  *[Symbol.iterator]() { yield* this.#cues; }
  *between(start, end) {                              // a second, named iterator
    for (const c of this.#cues) if (c.start >= start && c.end <= end) yield c;
  }
}
const track = new CaptionTrack();
[...track];                       // works
for (const c of track.between(10, 20)) render(c);

// 3. async generator — pagination as a flat loop
async function* allSlides(deckId, { signal } = {}) {
  let cursor = null;
  do {
    const page = await api.slides(deckId, { cursor, signal });
    yield* page.items;                                // yield each item, not the page
    cursor = page.nextCursor;
  } while (cursor);
}

for await (const slide of allSlides("d1")) {
  renderThumb(slide);             // pages are fetched lazily, as you consume
}
The sentence that makes this answer land

"An async generator turns pagination from a while loop with cursor bookkeeping into a for await…of that reads like a plain loop, and it fetches lazily — if the consumer stops early, the next page is never requested."

That is a real design benefit, not syntax appreciation, and it is the answer most candidates cannot give.

//    Must work on an INFINITE generator without hanging.
//    const naturals = function* () { let i = 0; while (true) yield i++; };
//    [...take(naturals(), 5)]  →  [0, 1, 2, 3, 4]

//    it to an array first, so that:
//      for (const [k, v] of iterableObject(widgetMap)) ...

// 3. paginate(fetchPage) — an async generator over a cursor API.
//    - yields individual items, not pages
//    - stops when nextCursor is null
//    - if the consumer breaks out of the loop early, no further page
//      is fetched (prove this with a counter)
Solution — open only after the timer 
// 1 — laziness is the point: we never touch item n+1
function* take(iterable, n) {
  if (n <= 0) return;
  let i = 0;
  for (const item of iterable) {
    yield item;
    if (++i >= n) return;        // `return` closes the source iterator too
  }
}

// 2 — entries without materialising an array
function iterableObject(obj) {
  return {
    *[Symbol.iterator]() {
      for (const key of Object.keys(obj)) yield [key, obj[key]];
    },
  };
}

// 3 — lazy pagination
async function* paginate(fetchPage, { signal } = {}) {
  let cursor = null;
  do {
    const page = await fetchPage({ cursor, signal });
    for (const item of page.items) yield item;
    cursor = page.nextCursor;
  } while (cursor);
}

Why breaking out early stops the fetching. When a for…of or for await…of loop exits via break, return or a throw, it calls the iterator's return() method. In a generator that resumes the body at the yield as if a return statement executed there — so the code after the yield, including the next fetchPage, never runs. Your counter will show exactly one page fetched if you break during the first page. This is also why try/finally inside a generator still runs its finally block on early exit, which is the correct place to release a resource.

Say that mechanism out loud. "Early exit calls return() on the iterator, which runs finally blocks and stops the generator" is a genuinely senior sentence, and almost nobody offers it.

What does gen.next(value) do with its argument?

Testing: two-way communication — the part most people miss.

"It becomes the result of the yield expression that the generator is currently paused at. So generators are two-way: they yield values out and receive values back in. That is precisely what makes a generator-based async runner possible — the driver resolves the yielded promise and pushes the value back in with next(value), or pushes an error in with throw(err) so try/catch inside the generator works."

Difference between yield and yield*?

Testing: a small precision check.

"yield x emits one value. yield* iterable delegates — it iterates that iterable and emits each of its values in turn, and it also forwards next, throw and return to the inner iterator. That is what makes recursive tree walking a two-line generator."

Why did async/await win over generator-based async?

Testing: historical judgement.

"Because it needed no runtime. Generator-based async required a library like co to drive it, and every codebase invented a slightly different driver. async/await standardised the driver into the language, gave proper stack traces, and made try/catch work naturally. Generators kept the jobs async/await cannot do — lazy sequences, infinite streams, and two-way communication, which is why Redux-Saga still uses them."

Chapter 3 — event loop, promises, async26 questions
State the loop in one sentence.

Run all sync code, drain the entire microtask queue, let the browser render, take exactly one task, repeat.

Name four things that create a microtask.

.then/.catch/.finally callbacks, resumption after await, queueMicrotask, MutationObserver.

How many microtasks run per turn? How many tasks?

All microtasks, including ones added during the drain. Exactly one task.

Can a microtask freeze the page?

Yes — a self-queueing microtask loop never lets the render step happen. The same loop with setTimeout stays responsive.

Where does requestAnimationFrame run?

In the render step: after microtasks drain, before style/layout/paint, and not at all in a background tab.

Does setTimeout(fn, 0) run in 0ms?

No — it queues a task to run no sooner than 0ms, after the stack empties and microtasks drain. Nested timers get clamped to ~4ms.

Is the event loop in the JS spec?

Jobs and run-to-completion are. The task/microtask/render model is the HTML spec — the host, not the language.

Three promise states, plus the two terms.

Pending, fulfilled, rejected. Settled means no longer pending; resolved means locked in to another promise and possibly still pending.

Is a resolved promise done?

Not necessarily — resolving with a pending promise leaves it resolved but pending.

Does .then on an already-settled promise run synchronously?

No. Always a microtask — so a function is never sometimes-sync, sometimes-async.

Does the new Promise executor run synchronously?

Yes, immediately. Only the .then callbacks are deferred.

What does .finally receive?

Nothing. It passes the original settled state through, unless it throws or returns a rejected promise.

Does an async function start asynchronously?

No — its body runs synchronously up to the first await, then returns a promise and suspends.

How many ticks does await cost?

One for a native promise or a plain value; more for a thenable. Returning a promise from a .then handler costs two extra for adoption and unwrapping.

Is return await an anti-pattern?

No — that guidance reversed. It is at least as fast, gives better stack traces, and inside a try it is the only version your catch can see.

Why doesn't forEach await?

It discards the callback's return value, so the promises are dropped. Use for…of or map + Promise.all.

What is a floating promise?

One nobody awaits or handles — you cannot know when it finished, and rejections become unhandled.

all vs allSettled?

all fails fast on the first rejection; allSettled never rejects and reports every outcome.

race vs any?

race takes the first to settle, including a rejection. any takes the first to fulfil and only rejects if all do, with an AggregateError.

What do the four do with an empty array?

all and allSettled fulfil with []; race stays pending forever; any rejects with AggregateError.

Does Promise.all cancel the losers?

No. They were already started and keep running; their results are just ignored. Use one shared AbortSignal for real cancellation.

Can a promise be cancelled?

No. Cancel the underlying work with AbortController and guard the write with a flag or sequence id.

Why can't try/catch catch a setTimeout throw?

The callback runs in a later task; the try block's frame is long gone.

Fix the out-of-order search results.

Abort the previous request, and discard any response whose sequence id is not the latest. Debounce reduces frequency but does not fix ordering.

What makes something iterable?

A [Symbol.iterator]() method returning an object with next() → { value, done }.

What happens when you break out of a for…of over a generator?

The iterator's return() is called, finally blocks run, and the generator stops — so the next page is never fetched.
