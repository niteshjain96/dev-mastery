Session 1 How JavaScript decides what a name means ~75 min

1 · The execution model

Question 1 Walk me through what happens when JavaScript runs your code. Common opener · sets the tone for the whole round
Say this

When a piece of code runs — a script, or a function call — the engine creates an execution context and pushes it onto the call stack. Setting up that context happens in two steps.

First, a creation step: the engine walks the code and creates the bindings for that scope before running a single line. Parameters and var declarations are created and initialised to undefined; function declarations are created and fully initialised, so they are callable straight away; let, const and class bindings are created but deliberately left uninitialised, which is what the temporal dead zone is. The context also records a reference to its outer environment, which is fixed by where the code is written, not by who called it.

Then the execution step runs the statements in order and does the actual assignments. When a name is used, the engine looks it up in the current environment record, then the outer one, and so on up to global — that walk is the scope chain. If it is never found, you get a ReferenceError.

Example

what you wrote
function renderSlide(slide) {
  console.log(typeof toPx);     // "function"  — declarations are ready
  console.log(scale);           // undefined   — var exists, no value yet
  console.log(dpr);             // ReferenceError — let exists, uninitialised

  var scale = slide.width / 960;
  let dpr = window.devicePixelRatio;

  function toPx(emu) { return (emu / 914400) * 96 * scale; }
}
what the engine has built before line 1 executes
renderSlide execution context
├─ environment record
│    slide : <the argument>
│    toPx  : <function object>   ← created AND initialised
│    scale : undefined            ← created, initialised to undefined
│    dpr   : <uninitialised>      ← created, NOT initialised  (TDZ)
└─ outer : <the module/global environment>   ← from where it was WRITTEN

Solution — open only after the timer

Reading this before you have written your own version converts a 40-minute skill into a 4-minute feeling.

// after the creation step, before any line runs:
function buildWidget(config) {
  // config : the argument
  // render : <function object>   — usable immediately
  // retries: undefined
  // id     : <uninitialised, TDZ>
  // nextId : <uninitialised, TDZ>

  render();                 // runs fine — and returns "<div data-id=" + TDZ read → ReferenceError
  ...
}

The bug: render() is callable on line 1 because function declarations are initialised in the creation step. But its body reads id, which is still in the temporal dead zone at that moment, so the call throws ReferenceError: Cannot access 'id' before initialization — from inside render, not from the line you are looking at.

The second bug is the same shape: nextId is an arrow function assigned to a let, so it is not callable before its line. Had render() not thrown first, config.id ?? nextId() would have.

This is the whole point of the two-step model: it tells you which of two identical-looking functions is safe to call early. Declarations are. Expressions assigned to variables are not.

Is "hoisting" actually in the specification, or is it a teaching metaphor?

Testing: have you read anything primary, or only blog posts?

"Yes, JavaScript moves declarations to the top of the file."

"Nothing physically moves; it just behaves as if declarations were at the top."

"The word does not appear as a mechanism in the spec — MDN itself calls it a colloquial term for four different behaviours. Nothing moves. The bindings are instantiated when the scope is entered, before any statement is evaluated, and 'hoisting' is the name we give to the observable effect of that."

What is the difference between scope and execution context?

Testing: static versus runtime. People blur these two constantly.

"They're basically the same thing."

"Scope is where a variable is visible; context is the environment a function runs in."

"Scope is lexical and static — fixed by where you wrote the code, known before it runs. An execution context is runtime — one is created per invocation and destroyed when it returns. Call a function three times and you get three contexts but one scope structure. That is also why recursion works: separate records, same lexical shape."

Does a function's scope chain come from where it was defined or where it was called?

Testing: lexical vs dynamic scoping — the single fact closures rest on.

"From where it's called."

"From where it was defined. The function object captures its outer environment at creation time, so calling it from somewhere else entirely does not change what names it can see. JavaScript is lexically scoped. The one thing that is decided by the call site is this — which is exactly why this confuses people who think scoping is dynamic."

What is in the global execution context, and does var differ from let there?

Testing: do you know why some globals show up on window and some do not?

"At the top level of a classic script, var and function declarations become properties of globalThis, so window.x works. let, const and class go into a separate declarative record — they are global in scope but are not properties of globalThis. In an ES module none of it lands on globalThis, because module scope is its own thing and top-level this is undefined."

2 · Hoisting, precisely

Question 2 What is hoisting? What gets hoisted and what doesn't? Extremely common · usually the second question asked
Say this

Hoisting is the name for the fact that declarations are processed when the scope is entered, before any code in it runs — so a name can be referenced above the line that declares it. It is not code movement; it is the order of binding instantiation.

It is not one behaviour, it is three. Function declarations are hoisted with their value, so you can call them before their line. var is hoisted as a name only and initialised to undefined, so reading it early gives undefined rather than an error. let, const and class are also hoisted — the binding exists from the top of the block — but they are left uninitialised, and touching them before their declaration throws. That region is the temporal dead zone.

Cross-questions

So is let hoisted or not?

Testing: the exact thing most candidates get wrong, because most tutorials get it wrong.

"No. Only var and functions are hoisted."

"Technically yes, but you can't use it before the declaration."

"Yes — the binding is created when the block is entered, it is just not initialised. Two function declarations with the same name in one scope — what happens?

Testing: do you know that declarations overwrite silently?

"The later one wins, silently, in non-strict and strict code alike — both are instantiated in the creation step and the last one processed is the value you get. That is a real bug source in long files. Doing the same with two lets of one name is a SyntaxError instead, caught before anything runs, which is the better failure mode."

What about a function declaration inside an if block?

Testing: are you honest about the messy corners?

"It's block-scoped in strict mode."

"In strict mode — so in any module or any modern build — it is block-scoped and hoisted to the top of that block only. "typeof is only safe for names that do not exist at all. In the TDZ the binding does exist, so this is not an unknown identifier — it is a known one you are not allowed to read yet. Making it return "undefined" would have hidden exactly the bug let was introduced to surface."

3 · var vs let vs const

Question 3 What's the difference between var, let and const? Near-certain · treated as a warm-up, scored as a filter
Why this question is a trap despite being easy

Everyone can answer it in one sentence, so a one-sentence answer scores zero. The interviewer is not checking whether you know; they are calibrating how much depth you volunteer unprompted. Give four axes, not one, and finish with the const nuance — then they skip ahead to harder questions, which is what you want.

Say this

They differ on four axes. Scope: var is function-scoped, let and const are block-scoped — any pair of braces, including a loop body or a try block. Initialisation: var starts as undefined; let and const sit in the temporal dead zone until their line runs. Redeclaration: var can be redeclared silently, let and const cannot — that is a SyntaxError. Global object: a top-level var in a classic script becomes a property of globalThis; let and const do not.

And the one people get wrong: const does not make a value immutable, it makes the binding unassignable. A const object can still have its properties changed. If I want the value frozen I need Object.freeze, and even that is shallow.

Example

// scope: the classic bug this fixes
function collectWidgets(slides) {
  for (var i = 0; i < slides.length; i++) { /* ... */ }
  console.log(i);            // slides.length — var leaked out of the loop

  for (let j = 0; j < slides.length; j++) { /* ... */ }
  console.log(j);            // ReferenceError — j never existed out here
}

// const binds the binding, not the value
const widget = { id: "w1", x: 0 };
widget.x = 120;              // fine — mutating the object
widget = { id: "w2" };       // TypeError: Assignment to constant variable

Object.freeze(widget);
widget.x = 999;              // silently ignored (throws in strict mode)
widget.style.fill = "red";   // still works — freeze is one level deep
Trap

Object.freeze being shallow is the follow-up to the const answer about seventy percent of the time. Have deepFreeze ready — it is the next drill for exactly that reason.

Solution — open only after the timer 
function deepFreeze(obj, seen = new WeakSet()) {
  if (obj === null || (typeof obj !== "object" && typeof obj !== "function")) return obj;
  if (seen.has(obj)) return obj;          // cycle guard
  seen.add(obj);

  Object.freeze(obj);
  for (const key of Reflect.ownKeys(obj)) {
    const desc = Object.getOwnPropertyDescriptor(obj, key);
    if (desc && "value" in desc) deepFreeze(desc.value, seen); // skip getters
  }
  return obj;
}

Three things a reviewer looks for, in order of how often they are missed:

  • The cycle guard. Without the WeakSet, w.self = w recurses until the stack dies. Mentioning cycles before they ask is a strong signal.
  • Not triggering getters. obj[key] would invoke an accessor, which can have side effects. Reading the descriptor avoids that. Almost nobody does this; it reads as senior.
  • Reflect.ownKeys rather than Object.keys, so symbol keys and non-enumerable properties are covered too.

Say out loud while writing: "freeze first, then recurse, so a cycle back to this object finds it already frozen and already in the set."

Cross-questions

Is const immutable?

Testing: binding versus value. The single most common imprecision in this topic.

"Yes, a const can't be changed."

"The binding is immutable, the value is not. const means you cannot reassign the name after initialisation. The object it points to is as mutable as any other. For actual immutability you need Object.freeze, and that is shallow, so for real trees you write a deepFreeze with a cycle guard."

Why does for (const item of list) work, when for (const i = 0; i < n; i++) throws?

Testing: per-iteration bindings — the setup for the closure question two sessions from now.

"Because for-of assigns a new variable each time."

"for…of creates a fresh binding per iteration and initialises it from the iterator, so nothing is ever reassigned — which is exactly what const allows. The C-style loop has one binding and an i++ afterthought that reassigns it, and reassignment is precisely what const forbids. So it is a TypeError on the second iteration, not a syntax error."

Is there a performance cost to let over var?

Testing: will you invent a number, or say you would measure?

"Yes, let is slower because of the TDZ checks."

"Not meaningfully. Engines statically prove most TDZ checks away, and the block scoping is resolved at compile time. Any difference is noise next to layout, network or a re-render. If someone claimed otherwise in a code review I would ask for a benchmark before changing anything."

Is there any reason to use var today?

Testing: dogma versus judgement.

"In new code, effectively no — const by default, let when it genuinely has to change. The honest exceptions are all legacy: var in an old script that relies on the global-object property, or on redeclaration across concatenated files. I would not rewrite working code purely to remove var; I would change it when I am already in that file for another reason."

4 · The temporal dead zone

Question 4 What is the temporal dead zone, and why does it exist? Common follow-up · the "why" half is where people stop
Say this

The temporal dead zone is the stretch between entering a scope and the moment a let, const or class declaration is evaluated. The binding exists for that whole stretch but holds no value, and any attempt to read or write it — including with typeof — throws a ReferenceError.

The word to stress is temporal. It is about time, not about position in the source. If a function defined above the declaration is called after it, that read succeeds. So the same line of code can throw or not throw depending only on when it runs.

It exists for two reasons. It makes const coherent — a constant must never be observable without its value. And it converts a class of silent undefined bugs, which surface three functions later as Cannot read properties of undefined, into a loud error at the exact line that is wrong.

Example

// 1 — position does not decide it; time does
function readCaption() { return caption; }   // written ABOVE the declaration

// readCaption();        → ReferenceError if called here
let caption = "Scene 1";
console.log(readCaption());                  // "Scene 1" — fine now


// 2 — the shadowing trap: the inner declaration poisons the whole block
let scale = 1;
function resize() {
  console.log(scale);   // ReferenceError — NOT 1
  let scale = 2;        // this line is what makes the line above throw
}

// 3 — the same with var would have silently logged undefined,
//     and your canvas would have rendered at NaN scale
Seedhi baat

TDZ ka matlab ye nahi hai ki variable exist nahi karta. Variable exist karta hai, bas usme value daalne se pehle chhoone par error aata hai. Isliye example 2 mein andar wala let scale bahar wale scale ko dhak deta hai — poore function block mein — aur upar wali line 1 print karne ke bajaye phat jaati hai.

Yaad rakhne ka tareeka: "naam register ho gaya, value baad mein aayegi, beech ka time zone hi dead zone hai."

Find and fix three TDZ bugs

function createCaptionTrack(cues) {

    cues: sorted,

  const findCue = (t) => sorted.find(c => t >= c.start && t < c.end);

console.log(createCaptionTrack([{ start: 2, end: 4 }, { start: 0, end: 1 }]));
Solution — open only after the timer

Three separate failures, and they do not all fire at once — the first one masks the rest:

  1. cues: sorted reads sorted while it is still in the TDZ. Throws immediately.
  2. duration: totalDuration() calls a hoisted function declaration — legal — but its body reads sorted, still in the TDZ. Same error, thrown from a different line than the one you are looking at.
  3. activeAt is safe, because findCue is only read when activeAt is called, which is after everything is initialised. This is the "temporal, not positional" point made concrete.
function createCaptionTrack(cues) {
  // fix: declare before use — initialisation order is the real fix,
  // not moving things into functions
  const sorted = [...cues].sort((a, b) => a.start - b.start);
  const findCue = (t) => sorted.find(c => t >= c.start && t < c.end);

  function totalDuration() {
    return sorted.length ? sorted[sorted.length - 1].end : 0;
  }

  return {
    cues: sorted,
    duration: totalDuration(),
    activeAt(t) { return findCue(t); },
  };
}

The lesson to state out loud: a function declaration being callable early does not make its body safe early. Hoisting moves the function, not the data it reads.

Cross-questions

Is the TDZ a compile-time or a runtime concept?

Testing: the "temporal" word. Most people answer positionally.

"Compile time — it's the code above the declaration."

"Runtime. The binding is marked uninitialised when the scope is entered and marked initialised when the declaration is evaluated; the error comes from reading it in between. That is why a function written above the declaration works perfectly if it is called after it — the source position never changed, only the time did."

Does the TDZ apply to function parameters?

Testing: depth. Most candidates have never thought about it.

"Yes, within the parameter list itself. Parameters are initialised left to right, so a default value may reference parameters to its left but not to its right — function f(a = b, b = 2){} throws when you call f(), while function f(b = 2, a = b){} is fine."

Could you get a TDZ error on a variable you never declared in that function?

Testing: do you understand that the declaration taints the whole block?

"Yes — by shadowing. If a block reads an outer scale but later declares its own let scale, that inner declaration owns the name for the entire block, so the earlier read throws instead of quietly finding the outer one. It is a genuinely surprising bug the first time you hit it, and it is the reason 'declare at first use' is a better rule than 'declare at the top'."

Why not just make let behave like var and initialise to undefined?

Testing: language-design reasoning, not memorisation.

"Because then const would be incoherent — you would be able to observe a constant holding undefined before its value, so it would have had two values in its lifetime. And practically, undefined is the worst possible default: it does not fail where the mistake is, it fails later, somewhere else, in a stack trace that points at innocent code."

Session 3 Closures: the question you cannot fumble ~75 min

5 · What a closure is

Question 5 What is a closure? Asked in roughly nine of ten JavaScript rounds
Say this

A closure is a function bundled together with the lexical environment it was created in. MDN's phrasing is worth borrowing directly: "the combination of a function bundled together (enclosed) with references to its surrounding state."

In practice it means a function keeps access to the scope where it was written, not where it is called — and it keeps that access after the outer function has already returned. Two consequences matter: the captured variables are held by reference, not copied, so the function sees later changes; and every call to the outer function produces a separate environment, so two closures made the same way do not share state.

And closures are not rare or advanced — they are created every time a function is created. Every callback, every event handler, every hook body is one.

Example

function makeRedrawScheduler(ctx) {
  let pending = null;                      // lives in the closure — private, per-instance

  return function schedule(draw) {
    if (pending !== null) cancelAnimationFrame(pending);
    pending = requestAnimationFrame(() => {
      draw(ctx);
      pending = null;
    });
  };
}

const scheduleSlideA = makeRedrawScheduler(ctxA);
const scheduleSlideB = makeRedrawScheduler(ctxB);   // its OWN pending

That eight-line function demonstrates all three interview points at once. Persistence: pending outlives the call to makeRedrawScheduler. Privacy: nothing outside can read or corrupt it — there is no scheduler.pending to poke. Independence: scheduleSlideA and scheduleSlideB each closed over their own environment, so cancelling one never touches the other.

The sentence that upgrades your answer

"A closure captures the binding, not the value." Say that unprompted and the interviewer usually skips the two easy follow-ups, because you have already answered them.

once(fn)

// Every later call returns the FIRST result without calling fn again.
// `this` and all arguments must pass through.
// Must work if fn returns undefined (i.e. don't use the result as the flag).

function once(fn) {
  // your code
}

const init = once(() => { console.log("init"); return Date.now(); });
init(); init(); init();   // logs "init" exactly once, same timestamp each time
Solution — open only after the timer 
function once(fn) {
  let called = false;         // separate flag — result may legitimately be undefined
  let result;
  return function (...args) {
    if (!called) {
      called = true;          // set BEFORE calling: guards re-entrant calls
      result = fn.apply(this, args);
      fn = null;              // optional: let the original be garbage collected
    }
    return result;
  };
}

What is being scored here, in the order an interviewer notices it:

  • A separate boolean flag rather than if (result === undefined). A function that legitimately returns undefined would be called every time.
  • function, not an arrow, plus fn.apply(this, args) — so obj.method = once(f) still gets the right this. An arrow here silently breaks method usage.
  • Setting the flag before invoking. If fn calls the wrapper again, the flag must already be set or you recurse.
  • fn = null is the senior touch — you are releasing the closure's reference so the original function and anything it captured can be collected. Mention it even if you do not write it.

function beginDrag(widget, startEvent) {

  window.addEventListener("pointerup", onUp);
}

function createStore(reducer, initialState) {
  let state = initialState;          // private: only reachable via the closure
  let listeners = [];

  function getState() { return state; }

  function dispatch(action) {
    state = reducer(state, action);
    // copy before iterating: a listener may subscribe/unsubscribe mid-notify
    for (const l of [...listeners]) l();
    return action;
  }

  function subscribe(listener) {
    listeners.push(listener);
    let subscribed = true;           // per-subscription flag, own closure
    return function unsubscribe() {
      if (!subscribed) return;       // idempotent
      subscribed = false;
      const i = listeners.indexOf(listener);
      if (i >= 0) listeners.splice(i, 1);
    };
  }

  dispatch({ type: "@@INIT" });      // let the reducer seed the default state
  return { getState, dispatch, subscribe };
}

Two closures are nested here and being able to say so out loud is the point: getState, dispatch and subscribe share one environment holding state and listeners; and each call to subscribe creates a second, inner environment holding that subscription's own subscribed flag and listener.

The [...listeners] copy is the detail that separates a memorised answer from an engineered one. Without it, a listener that unsubscribes itself during notification shifts the array underneath the loop and the next listener is skipped. Real Redux solves this with a current/next listener pair for the same reason.

7 · The 3-3-3 loop puzzle

Question 7 Why does this print 3, 3, 3? Now fix it in three different ways. The most-asked closure follow-up in existence 
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3 3 3

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0 1 2
Say this

var is function-scoped, so there is exactly one i and all three callbacks close over that same binding. The loop is synchronous and finishes before any timer callback runs — timers go to the task queue and only run once the stack is empty — so by the time they execute, i is already 3.

let in the loop header is special-cased by for: each iteration gets a fresh binding. Precisely, after the body runs, a new scope is created, the previous iteration's values are copied into it, and only then does i++ run — in the new scope. So each callback closed over a different i, holding the value that iteration had.

The general principle: it is not about setTimeout, and not about asynchrony. It is one binding shared by three closures versus three bindings, one each.

8 · Closures and memory leaks

Question 8 Can closures cause memory leaks? Have you ever found one? Senior-level differentiator · almost nobody has the second half
Say this

Closures do not leak by themselves — garbage collection is reachability-based, so a closure is collected as soon as nothing references it. The leak happens when something long-lived holds the closure, and the closure in turn keeps a large object reachable.

The four shapes I look for: a listener added to a long-lived target like window or document and never removed; an interval or timer never cleared; a subscription to a store or observer with no unsubscribe; and a closure kept in a module-level cache or Map that grows without bound.

The symptom in a single-page app is detached DOM: the component unmounted, the nodes were removed from the document, but a surviving handler still references them, so the whole subtree stays in memory. You find it in the DevTools Memory panel — take a heap snapshot, filter for Detached, and read the retainer path back to whatever is holding it.

Example — a leak in a canvas editor, and its fix

// LEAKS. Every time this slide mounts, another handler is added to window,
// and each one captures `bitmap` — a full-resolution ImageBitmap.
function mountSlide(slide, canvas) {
  const ctx = canvas.getContext("2d");
  const bitmap = slide.renderToBitmap();      // several MB

  window.addEventListener("resize", () => {
    ctx.drawImage(bitmap, 0, 0);
  });
}

// FIXED. Return a teardown; the listener and everything it captured
// become unreachable the moment it runs.
function mountSlide(slide, canvas) {
  const ctx = canvas.getContext("2d");
  let bitmap = slide.renderToBitmap();

  const onResize = () => { if (bitmap) ctx.drawImage(bitmap, 0, 0); };
  window.addEventListener("resize", onResize);

  return function unmount() {
    window.removeEventListener("resize", onResize);
    bitmap.close?.();     // release the GPU-side resource explicitly
    bitmap = null;        // drop the reference even if something still holds onResize
  };
}
The detail that makes this answer senior

In V8, all closures created in the same function scope share one context object. So a tiny callback that never touches bitmap can still keep it alive, purely because a sibling closure in the same scope references it. That is why the fix sets bitmap = null rather than trusting the small handler to be harmless — and it is why "but my closure does not use the big object" is not a safe argument.

function createListenerBag() {
  let entries = [];                 // closed over — no external access
  let cleared = false;

  return {
    on(target, type, handler, options) {
      if (cleared) return () => {};
      target.addEventListener(type, handler, options);
      const off = () => target.removeEventListener(type, handler, options);
      entries.push(off);
      return off;                   // allow removing just this one
    },
    timer(id, kind = "interval") {
      if (cleared) { kind === "interval" ? clearInterval(id) : clearTimeout(id); return; }
      entries.push(() => (kind === "interval" ? clearInterval(id) : clearTimeout(id)));
      return id;
    },
    clear() {
      if (cleared) return;          // idempotent
      cleared = true;
      for (const off of entries) { try { off(); } catch {} }
      entries = [];                 // drop references so captured targets can be collected
    },
  };
}

9 · Debounce vs throttle

Question 9 What's the difference between debounce and throttle? Implement debounce. Near-certain · and it reappears inside the machine coding round
Say this

Both limit how often a function runs, but they answer different questions. Debounce waits for a pause: it postpones the call until the events have stopped for N milliseconds, so a burst of fifty events produces one call. You use it when only the final state matters — a search box, autosave, a resize that triggers an expensive re-layout.

Throttle enforces a rate: it guarantees at most one call every N milliseconds during a continuous stream. You use it when the intermediate states matter and you just cannot afford all of them — scroll position, pointer-move while dragging, a canvas redraw capped at one per frame.

One sentence to remember it by: debounce collapses a burst into its last event; throttle samples a stream at a fixed rate.

Solution — open only after the timer 
function debounce(fn, wait, { leading = false, trailing = true } = {}) {
  let timer = null;
  let lastArgs = null;
  let lastThis = null;
  let result;

  function invoke() {
    const args = lastArgs, ctx = lastThis;
    lastArgs = lastThis = null;
    result = fn.apply(ctx, args);
    return result;
  }

  function debounced(...args) {
    lastArgs = args;
    lastThis = this;                       // must be a normal function, not an arrow

    const isFirst = timer === null;
    if (timer !== null) clearTimeout(timer);

    if (leading && isFirst) invoke();

    timer = setTimeout(() => {
      timer = null;
      // don't double-fire when leading already ran and nothing new arrived
      if (trailing && lastArgs) invoke();
    }, wait);

    return result;                         // last known result, like lodash
  }

  debounced.cancel = function () {
    if (timer !== null) clearTimeout(timer);
    timer = null;
    lastArgs = lastThis = null;
  };

  debounced.flush = function () {
    if (timer !== null && lastArgs) {
      clearTimeout(timer);
      timer = null;
      return invoke();
    }
    return result;
  };

  debounced.pending = () => timer !== null;

  return debounced;
}

Scoring notes, in the order an interviewer checks them:

  • function, not arrow, for debounced — otherwise this is lost and input.oninput = debounce(...) breaks.
  • Storing the latest args, not the first. The whole point is that the final call wins.
  • clearTimeout before setting a new one. Forgetting it means every call eventually fires — a delay, not a debounce.
  • Clearing lastArgs after invoking, so a leading-edge call with no follow-up does not fire twice at the trailing edge. This is the bug in most hand-written versions.
  • Nulling lastThis/lastArgs in cancel — otherwise you retain the arguments, which in a React app can mean retaining a whole event object or component scope.

Now say the closure sentence out loud: "timer, lastArgs and result live in the closure, so the returned function has memory between calls without any external state." That single line converts an implementation into an explanation.

"I would not use a timer at all — I would coalesce into requestAnimationFrame. Store the latest pointer position in a closure variable, schedule one rAF if none is pending, and draw once per frame. A 16ms throttle is fighting the browser's clock rather than aligning with it, and it can drop a frame or draw twice in one. That is exactly what the redraw scheduler from question 5 does."

Why does your debounced function need cancel?

Testing: have you used this in a real component lifecycle?

"Unmount. If a component is removed while a debounced save is pending, that call will still fire and touch state that no longer exists, or send a request for a screen the user has left. Every debounce in a React app should be cancelled in the effect's cleanup. It is the same discipline as removing a listener."

10 · Modules, IIFEs and currying

Question 10 What's the module pattern, and is an IIFE still useful today? Occasional · but the currying half is a frequent machine-coding warm-up
Say this

The module pattern is an immediately-invoked function that returns an object of public methods, all closing over variables that stay private. Before ES modules it was the only way to avoid polluting the global scope and the only way to get privacy at all.

Today ES modules do that natively — a module has its own scope, and anything not exported is already private — so the pattern is largely historical. Where an IIFE is still genuinely useful is narrower: creating a scope inline for a one-off computed constant, running async top-level code in a non-module script, and isolating a script you are injecting into a page you do not control.

Currying and partial application are the same closure mechanism pointed at arguments instead of privacy: each call captures some arguments and returns a function waiting for the rest.

Example

// module pattern — one shared private environment
const historyStack = (function () {
  const undoStack = [];      // unreachable from outside
  const redoStack = [];

  return {
    push(cmd) { undoStack.push(cmd); redoStack.length = 0; },
    undo() { const c = undoStack.pop(); if (c) { redoStack.push(c); c.revert(); } },
    redo() { const c = redoStack.pop(); if (c) { undoStack.push(c); c.apply(); } },
    get depth() { return undoStack.length; },
  };
})();

// the modern equivalent — same privacy, no ceremony
// history.js
const undoStack = [];        // private simply by not being exported
export function push(cmd) { /* ... */ }

// partial application — capture config once, call with one argument forever after
const makeEmuConverter = (dpi) => (emu) => (emu / 914400) * dpi;
const toPx = makeEmuConverter(96);     // the .pptx hot path
toPx(914400);                          // 96

Solution — open only after the timer 
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) return fn.apply(this, args);
    return function (...rest) {
      // new array every time — never mutate `args`, or `base` would
      // accumulate and base(10) after base(4) would break
      return curried.apply(this, [...args, ...rest]);
    };
  };
}

The bonus is the whole test. If you write args.push(...rest) instead of building a new array, the captured args is mutated and the partially applied base is poisoned after its first use. Each closure must own its own arguments array — which is the same per-instance environment idea from question 5, showing up for the fourth time in this chapter.

Known limits worth saying out loud, because they are the follow-up: fn.length ignores default parameters and rest parameters, so (a, b = 2) => … reports an arity of 1. For variadic functions you need an explicit arity argument: curry(fn, 3).

Cross-questions

Difference between currying and partial application?

Testing: precision. People use the words interchangeably; they are not.

"Currying transforms an n-argument function into a chain of n one-argument functions. Partial application fixes some arguments and returns a function taking the rest — it does not care about arity. bind is partial application, not currying. Both are built on the same closure capture."

Do you use currying in production React?

Testing: honesty over buzzwords.

"Rarely in its pure form. Partial application, constantly — onChange={handleField('title')}, pre-configured converters, selector factories. Full currying tends to hurt readability and defeats TypeScript inference in places. It is worth knowing because it is asked, not because it is common."

If ES modules give privacy, is the module pattern dead?

Testing: dogma versus nuance.

"For structuring an app, yes — use modules. The pattern survives in three places: a factory that needs per-instance privacy, since module scope is per-file and shared, not per-instance; inline scripts and snippets injected into pages you do not own; and reading older code, which is the real reason to recognise it."

Chapter 1 — scope, closures, execution24 questions
Define a closure in one sentence.

A function bundled with references to the lexical environment it was created in, which it keeps even after the outer function has returned.

When is a closure created?

At function creation time — every function creation captures its surrounding environment, whether or not it is ever called.

Value or reference?

Reference to the binding. The closure sees later changes to the captured variable.

Two functions created in the same scope — separate closures or shared?

Separate function objects, one shared environment. They can see each other's writes.

What determines a function's scope chain?

Where it was written, not where it is called. Lexical scoping.

What is decided by the call site instead?

this — which is Chapter 2, and why people who assume dynamic scoping get confused.

Is let hoisted?

Yes — the binding is created on entering the block, but left uninitialised. That uninitialised window is the TDZ.

What does typeof do on a TDZ variable?

Throws ReferenceError. It is only safe for names that were never declared.

ReferenceError vs TypeError when calling too early?

var f = function(){} gives TypeError: f is not a function; let f = () => {} gives ReferenceError.

Why is the TDZ called "temporal"?

It is about execution time, not source position. A function written above the declaration works if it is called after it.

Is const immutable?

The binding is; the value is not. Object.freeze for the value, and it is shallow.

Why does for (const x of list) work?

Fresh binding per iteration, initialised rather than reassigned — so nothing violates const.

Why does for (const i = 0; …; i++) throw?

i++ reassigns the binding — TypeError on the second iteration.

Why does the var loop log 3, 3, 3?

One binding shared by three closures; the loop finishes before any callback runs.

Why does let log 0, 1, 2 and not 1, 2, 3?

New scope per iteration, value copied forward, and i++ runs in the new scope — never in the one already captured.

Does let fix it if declared outside the loop header?

No. let k = 0; for (; k < 3; k++) logs 3, 3, 3 — the per-iteration binding only applies to the header declaration.

Name a fix that captures nothing at all.

setTimeout(console.log, 0, i) — extra arguments are forwarded, so the value is passed at schedule time.

Do closures leak memory?

Not by themselves. They leak when something long-lived holds them and they keep a large object reachable.

How do you find one?

Heap snapshot, filter Detached, follow the retainer path back to the holder.

Debounce vs throttle in one line?

Debounce collapses a burst into its last event; throttle samples a continuous stream at a fixed rate.

Which for a search box, which for scroll?

Debounce for search; throttle — or better, requestAnimationFrame — for scroll and pointermove.

Why must debounce return a normal function, not an arrow?

To forward this, so it still works when assigned as a method or a DOM handler.

Currying vs partial application?

Currying converts an n-ary function into n unary ones; partial application fixes some arguments and returns a function for the rest. bind is the latter.

Where do closures bite you in React?

Stale closures — an effect or callback captures the props and state of the render that created it.
